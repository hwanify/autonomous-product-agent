# 검증 — 요리용 멀티 타이머 (slug: multi-timer)

> Run #4 초안 → Run #5 1차 보완(기각, Critic REWORK) → Run #5 2차 보완(이번 버전). 두 번째 Critic 이 지적한 결함(엉뚱한 경쟁자에 근거 전이, 기술적 과잉일반화)을 반영해 다시 작성.

## 이전 버전의 오류 (Critic 2차 지적, 인정함)

1. **엉뚱한 경쟁자 조사**: 원래 Gap 근거는 "Multi Kitchen & Cooking Timer"의 무음 버그였는데, 이번엔 다른 앱(MultiTimer)의 알림 문제만 조사해놓고 그 결론("OS 레벨 제약")을 원래 버그에 그대로 전이시켰다. Multi Kitchen & Cooking Timer 의 버그가 정말 OS 제약인지 자체 구현 결함인지는 확인된 바 없다 — **이 부분은 근거 없음, 폐기한다.**
2. **기술적 과잉일반화**: "우리도 동일하게 실패한다"고 단정했는데, 이는 검증하지 않은 채 내린 성급한 비관이다. iOS 의 **시간 기반 로컬 예약 알림**(예: `expo-notifications`의 `scheduleNotificationAsync` + 초 단위 트리거)은 OS(`UNUserNotificationCenter`)가 스케줄을 쥐고 있어 앱이 백그라운드/종료 상태여도 배너·소리를 울리도록 설계되어 있다는 것이 iOS 의 일반적 동작이다. 반면 이번 실행에서 추가로 찾은 expo-notifications 관련 이슈들(GitHub)은 대부분 "알림을 **탭했을 때** 실행되는 JS 콜백(NotificationResponseReceivedListener)이 앱이 killed 상태였을 때 안 붙는다"는, **알림 표시 자체가 아니라 탭 이후 반응 처리**에 관한 별개 문제였다. 즉 "타이머가 끝나면 소리/배너가 뜨는가"와 "알림을 탭했을 때 앱이 그 정보를 아는가"는 다른 문제이고, 우리 핵심 요구사항(첫 번째)에는 앞의 이슈들이 직접 적용되지 않는다.
3. **조합형 니치(여러 프리셋을 한 앱에 모아 동시 실행)를 근거 없이 낮춤**: "범위가 커질 것"이라는 추측만으로 Differentiation 을 깎았다 — 실제로 이 조합의 직접 경쟁자를 찾지 못했다는 사실 자체는 오히려 중립적으로 다뤄야 한다(빈틈일 수도, 그냥 수요가 없어서일 수도 있음 — 확신 없음).

## 재점수 (2차 보완, 가설 명시)

| 기준 | 점수 | 근거 |
|---|---|---|
| Pain | 4 | 타이머 알림 실패 시 요리를 태우는 실질적 피해 — 변화 없음 |
| Gap | 3 | 경쟁 앱 다수가 라벨+다중 타이머를 제공하지만(Gap 하향 요인), "확실하게 울리는 알림"(OS 스케줄 기반)을 명시적으로 내세우는 경쟁 앱은 조사에서 발견되지 않음(Gap 상향 요인) — **단, 경쟁 앱들이 실제로 이 부분에서 얼마나 실패하는지는 정량적으로 확인 못 함(가설)** |
| Feasibility | 5 | `expo-notifications` 의 시간 기반 트리거로 구현 가능. 변화 없음 |
| Demonstrability | 5 | 변화 없음 |
| Differentiation | 3 | "절대 놓치지 않는 알림 + 완전 무료·광고 없음"은 한 문장으로 설명 가능한 차별점이다. 단, 이 차별점이 실제로 지켜지는지는 **검증되지 않은 가설**이다 |
| **합계** | **20** | 기준(18점) 통과, Feasibility≥4 충족 |

## 왜 이 선정이 틀렸을 수 있는가 (반대 논거, 정직하게 남김)

1. **핵심 가설이 미검증 상태다.** "우리 앱은 백그라운드/종료 상태에서도 타이머 알림이 확실히 울린다"는 것이 유일한 실질적 차별점인데, 이걸 실제 기기(Expo Go)에서 검증한 적이 없다. 만약 Expo Go 앱 자체의 제약(사파리처럼 서드파티 러너라 백그라운드 스케줄링에 제한이 있을 가능성)으로 이 가설이 틀리면, 차별점이 통째로 사라진다.
2. **경쟁 앱들이 실제로 이 부분에서 못한다는 정량적 근거가 약하다.** 리뷰 스니펫 몇 개로 판단했을 뿐, MultiTimer 나 다른 앱이 실제로 시간 기반 로컬 알림을 올바르게 구현했을 수도 있다(즉 우리보다 나을 수도 있음).
3. **시장이 여전히 붐빈다.** 최소 6개 이상의 직접 경쟁 앱이 있고, "알림 신뢰성"이라는 한 가지 축만으로 사용자를 끌어오기엔 유통력(앱스토어 노출)이 부족할 수 있다 — 다만 이 MVP는 사람 1명이 Expo Go 로 쓰는 것이 목표(mission.md §1, §5)이므로 유통력 문제는 이번 성공 기준에서 우선순위가 낮다.

## 결론: 선정 (SELECT 제안), 첫 구현 작업으로 핵심 가설 검증을 명시

재점수 합계 20점으로 mission.md §4 기준을 통과했고, "확실한 알림"이라는 차별점은 한 문장으로 설명 가능하며 기술적으로 달성 가능해 보인다(가설). 이 가설이 잘못되면 차별점이 사라지므로, **design 단계 MVP 범위의 첫 구현 작업으로 "앱이 백그라운드/종료 상태에서도 예약된 로컬 알림이 소리·배너와 함께 실제로 울리는지 실기기(Expo Go)에서 검증"을 명시적으로 포함시킬 것을 제안한다** — 이 검증이 실패하면 즉시 이 후보를 재검토(pivot)해야 한다는 조건부 선정이다.

**multi-timer 후보를 선정**하고 `phase="design"` 전이를 제안한다.

(주: 이 결론은 Critic 게이트 통과 전까지 잠정적이다. 이번이 세 번째 제출이며, 이전 두 번(기각 2회)의 Critic 지적을 모두 반영해 결론을 뒤집었다 — 이는 과거 결론에 대한 고집이 아니라 새 근거(로컬 알림의 OS 레벨 동작 방식 확인)에 따른 정정이다.)
