# 검증 — 요리용 멀티 타이머 (slug: multi-timer)

> Run #4, T-005. docs/research/multi-timer.md (Run #2, 새 조사 없이 기존 자료 재검토)를 근거로 mission.md §4 기준 재점수 + 반대 논거 + 선정/기각 결론.

## 재점수 (조사 이전 vs 이후)

## 왜 실패할까 (반대 논거)

1. **이미 무료·광고 없음·라벨·다중 타이머를 다 갖춘 앱(MultiTimer)이 존재한다.** 우리가 만들 것과 핵심 기능이 사실상 동일하다. 사용자가 갈아탈 이유가 "약간 더 안정적일 것 같다"는 검증되지 않은 기대뿐이라면 약하다.
2. **우리의 유일한 차별화 근거(알림 신뢰성)는 검증되지 않았다.** 버그가 확인된 곳은 MultiTimer가 아니라 다른 경쟁 앱(Multi Kitchen & Cooking Timer)이다. 정작 가장 강력한 경쟁자가 이미 안정적이라면 차별점 자체가 사라진다.
3. **"요리용" 포지셔닝의 잠재적 진짜 차별점(조리 프리셋 라이브러리 — 예: "라면 4분", "계란 완숙 10분" 같은 미리 정의된 프리셋)은 이번 조사에서 확인도 반박도 되지 않았다.** 이 각도라면 이야기가 다를 수 있지만, 지금 이 문서가 평가하는 후보는 ideas-1.md 에 정의된 "라벨 붙는 범용 멀티 타이머"이지 "조리 프리셋 특화 앱"이 아니다 — 범위를 바꾸려면 새 아이디어로 다시 제안해야 한다.
4. (재반론 시도) "점수가 18점으로 기준을 통과했으니 진행해야 한다"는 주장은 근거 없는 낙관이다. 합계는 Pain·Feasibility·Demonstrability 가 떠받치고 있을 뿐, mission.md §4 가 요구하는 "명확한 빈틈"(Gap)과 "한 문장 차별점"(Differentiation)은 둘 다 2점(낮음)으로, 이 아이디어를 시장에 내놓을 근거가 약하다는 뜻이다.

## 결론: 기각 (REJECT 제안)

숫자 합계(18점)는 기준을 통과하지만, Gap 과 Differentiation 이 모두 낮아 "명확한 빈틈"이라는 mission.md 핵심 요구를 충족하지 못한다. 현재 정의된 범용 "라벨형 멀티 타이머"로는 이미 존재하는 무료 경쟁 앱(MultiTimer)과 실질적으로 차별화되지 않는다. **이 후보(현재 범위대로)를 기각**할 것을 제안한다.

조리 프리셋 라이브러리 각도는 별도 아이디어로 다음 cycle 에서 재도전할 가치가 있다는 점을 decisions.md 에 메모로 남긴다(§4.2 "왜 실패할까" 이었지만 완전히 죽은 방향은 아님).

(주: 이 결론은 Critic 게이트 통과 전까지 잠정적이다.)
