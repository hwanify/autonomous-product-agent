# MVP 설계 — 요리용 멀티 타이머

> Run #6, T-006. docs/validation/multi-timer.md (Run #5, Critic PASS 3차) 선정 근거를 바탕으로 MVP 설계.
> **선정 조건**: Critic이 명시한 조건부 선정 — "Expo Go 실기기에서 앱 종료/백그라운드 상태에서도 예약 로컬 알림이 소리+배너로 울리는지" 검증이 이 설계의 가장 중요한 전제이며, 이를 첫 구현 작업(T-007)으로 명시한다. 실패 시 즉시 explore로 pivot한다(D-007).

## 1. MVP 범위

### 필수 기능 (In scope)
1. **타이머 생성**: 라벨(텍스트, 예: "라면", "계란")과 시간(분:초)을 입력해 타이머를 만든다.
2. **다중 동시 실행**: 여러 타이머를 동시에 리스트로 실행하고, 각각 남은 시간을 표시한다.
3. **확실한 종료 알림**: 타이머가 끝나면 로컬 알림(소리+배너+진동)이 울린다. **앱이 백그라운드거나 완전히 종료된 상태에서도 동작해야 한다** — 이것이 이 제품의 유일한 실질적 차별점(mission.md §4 Differentiation)이므로 필수 중의 필수다.
4. **일시정지/재개/취소**: 실행 중인 개별 타이머를 멈추거나 다시 시작하거나 삭제할 수 있다.
5. **프리셋 저장/재사용**: 자주 쓰는 타이머(라벨+시간)를 저장해두고 한 번의 탭으로 다시 시작할 수 있다 (`AsyncStorage`).

### 제외 기능 (Out of scope, 이번 MVP에서는 안 함)
- 서버 동기화·계정·클라우드 백업 (mission.md §3, 비용 0원/서버 없음 원칙)
- Apple Watch 연동
- 소리·아이콘 커스터마이징 (기본 알림음만 사용)
- 위젯 / Live Activity / Dynamic Island (Expo Go 환경에서 지원 범위가 불확실하고 복잡도가 높음 — 향후 improve 단계 후보)
- 다국어 (한국어 UI만)
- 공유·소셜 기능

## 2. 핵심 사용자 시나리오 (mission.md §5 성공 기준)

> 저녁에 라면(4분)과 계란(9분)을 동시에 삶는다.
> 1. 사용자가 앱을 열고 "새 타이머"에서 라벨 "라면", 시간 4:00 을 입력해 시작한다.
> 2. 이어서 라벨 "계란", 시간 9:00 을 입력해 시작한다. 홈 화면에 두 타이머가 동시에 카운트다운된다.
> 3. 사용자는 화면을 끄고 다른 일(설거지 등)을 한다 — 앱은 백그라운드/화면 꺼짐 상태.
> 4. 4분 뒤 "라면" 타이머가 끝나면 화면이 꺼져 있어도 소리+배너 알림이 울린다. 사용자가 알림을 확인하고 불을 끈다.
> 5. 9분 뒤 "계란" 타이머도 같은 방식으로 알림이 울린다.
> 6. 다음날, 사용자는 저장된 프리셋에서 "라면 4분"을 탭 한 번으로 다시 시작한다.

이 시나리오 전체가 Expo Go 로 실행한 실제 아이폰에서 동작하는 것이 MVP 완료 정의다.

## 3. 화면 흐름

```
[홈 화면]
 ├─ 실행 중인 타이머 리스트 (라벨, 남은시간 텍스트+진행바, 일시정지/재개, 취소 버튼)
 ├─ 저장된 프리셋 리스트 (탭하면 바로 새 타이머로 시작)
 └─ "+ 새 타이머" 버튼
       └─ [새 타이머 모달]
            ├─ 라벨 입력창
            ├─ 시간 입력(분/초)
            ├─ "프리셋으로 저장" 체크박스(선택)
            └─ 시작 버튼 → 홈 화면으로 복귀, 타이머 리스트에 추가됨
```
최초 실행 시 알림 권한 요청 프롬프트(OS 표준) 1회.

화면은 1개(홈) + 모달 1개로 최소화한다(mission.md Feasibility, 5~10회 실행 내 완성).

## 4. 기술 구조

- **Expo managed workflow**, `npx create-expo-app` 기반. `ios/`, `android/` 생성 안 함(prebuild/eject 금지, CLAUDE.md §2 기술원칙).
- **디렉터리**: `product/` 아래에 앱 전체.
  - `lib/timer.ts` — 순수 함수/타입: 타이머 생성, 남은시간 계산(타임스탬프 기반, 일시정지 시간 보정), 상태 전이(running/paused/done)
  - `lib/notifications.ts` — `expo-notifications` 래퍼: 타이머 시작 시 종료 시각에 맞춰 로컬 알림 예약(`scheduleNotificationAsync`, seconds 트리거), 취소/일시정지 시 예약 취소, 권한 요청
  - `lib/presets.ts` — `AsyncStorage` 기반 프리셋 CRUD
  - `App.tsx` / `screens/Home.tsx` / `components/TimerCard.tsx`, `components/NewTimerModal.tsx` — UI, 위 lib 모듈을 사용하는 얇은 레이어
- **핵심 설계 원칙(신뢰성)**: 화면에 보이는 카운트다운은 `setInterval` 로 매초 갱신해도 되지만, **실제 "종료 알림"은 반드시 OS 에 예약된 `expo-notifications` 트리거에 의존**한다 — JS 타이머(`setTimeout`/`setInterval`)에 종료 알림을 의존시키지 않는다. 이것이 D-007 에서 지적된 "경쟁 앱의 무음 버그가 아마도 JS 타이머 기반 구현 때문일 것"이라는 가설에 대한 우리 쪽 설계 대응이다.
- **저장**: `@react-native-async-storage/async-storage` (프리셋만 영속화, 실행 중인 타이머 상태는 세션 한정도 허용 — 앱 kill 후 재실행 시 타이머 리스트가 비어도 MVP 범위는 만족. 단, 예약된 로컬 알림 자체는 OS 가 들고 있으므로 앱을 다시 안 열어도 알림은 울린다).
- **패키지**: `expo-notifications`, `@react-native-async-storage/async-storage` 만 추가(각각 `npx expo install`). 그 외 UI 라이브러리는 기본 React Native 컴포넌트로 충분하면 추가하지 않는다.

## 5. 테스트 계획

- **자동화 테스트** (`jest-expo` 프리셋, `product/` 안에서 `npm test`):
  - `lib/timer.ts`: 남은시간 계산, 일시정지→재개 시 정확한 시간 보정, 여러 타이머 동시 관리(리스트 add/remove/update)
  - `lib/notifications.ts`: 예약/취소 호출이 올바른 인자로 이루어지는지 (expo-notifications 모킹)
  - `lib/presets.ts`: 저장/불러오기/삭제 (AsyncStorage 모킹)
- **수동 시나리오 (실기기, Expo Go)**:
  - **(최우선, T-007) 백그라운드/종료 상태 알림 검증**: 타이머를 시작하고 앱을 홈 화면으로 보내거나 완전히 스와이프해서 종료한 뒤, 예약된 시간에 소리+배너가 뜨는지 확인. **이 검증이 실패하면 이 제품 선정 자체를 재검토(pivot)한다** (D-007).
  - 위 §2 의 핵심 시나리오(라면+계란 동시 타이머) 전체를 실기기에서 실행.
  - 프리셋 저장 후 앱 재시작 → 프리셋이 남아있는지 확인.

### 알려진 한계 (Critic 지적, 설계상 수용)
- 실행 중이던 타이머 상태는 이번 MVP에서 영속화하지 않는다(프리셋만 영속). 알림이 울린 뒤 사용자가 앱을 다시 열었을 때 이미 끝난 타이머가 리스트에서 사라져 있는 것은 **의도된 동작**으로 취급한다(예약된 알림 자체는 OS가 들고 있으므로 앱을 안 열어도 울린다 — 리스트 UI 복원은 범위 밖). 이 부분이 실사용에서 불편하면 review 단계의 개선 후보로 남긴다.
- Jest 유닛 테스트는 `expo-notifications` 를 모킹하므로 "테스트 통과"가 "실제 알림이 울린다"를 보장하지 않는다 — 그래서 T-008 의 실기기 수동 검증을 별도 필수 게이트로 둔다.

## 7. 이 설계가 왜 틀렸을 수 있는가 (자기 반박)
- T-007 검증이 실패할 가능성은 실제로 낮지 않다 — Critic 이 지적한 대로 Expo Go 는 네이티브 빌드가 아니라 서드파티 컨테이너 앱이라, 시간 기반 로컬 알림이 네이티브 앱과 동일하게 종료 상태에서 발화한다는 보장이 없다. 이 검증이 이 설계 전체의 성패를 가른다.
- 화면 1개로 최소화한 설계가 지나치게 단순해서 "실제로 쓰고 싶은 수준"(mission.md §1)에 못 미칠 수 있다 — 다만 이는 review/improve 단계에서 다룰 문제로 보고 MVP 범위에서는 의도적으로 제외했다.
- 프리셋 기능이 mission.md §4 Differentiation 근거로 쓰이진 않았지만(핵심 차별점은 알림 신뢰성), 사용성상 필요해서 포함했다 — 만약 T-007~T-011 을 5~10회 실행 안에 못 끝내면(Feasibility 리스크) 프리셋(T-010)을 가장 먼저 잘라낼 후보로 삼는다.
