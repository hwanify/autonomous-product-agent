## 2. 수동 시나리오 (사람의 실기기가 필요 — 에이전트가 직접 할 수 없음)

mission.md §5 성공 기준("핵심 사용자 시나리오 1개가 Expo Go 로 실행한 아이폰에서 끝까지 동작")과 docs/design/mvp.md §2 의 핵심 시나리오는 실제 아이폰에서만 확인 가능하다. 이 에이전트는 GitHub Actions/Claude Code 컨테이너에서 실행되며 아이폰이 없다.

**아직 검증되지 않음 (T-015 로 사람에게 요청 예정):**
1. **[핵심, D-007/D-011 조건] 백그라운드/종료 상태 알림**: 타이머를 시작하고 화면을 끄거나 앱을 완전히 종료했을 때 예약 시각에 소리+배너 알림이 실제로 오는가. — 이것이 이 제품 선정의 유일한 실질적 차별점이며, 실패하면 pivot 조건이 발동한다.
2. **여러 타이머 동시 실행**: "라면 4분"과 "계란 9분"을 동시에 시작했을 때 화면에 둘 다 정확히 표시되고, 각각 제때 알림이 오는가.
3. **일시정지→재개**: 일시정지 후 남은 시간이 화면에 유지되고, 재개하면 그 시점부터 정확히 카운트다운되며 알림도 그 시점 기준으로 다시 울리는가.
4. **프리셋**: 저장한 프리셋으로 앱을 재시작해도 목록이 남아있고, 탭 한 번으로 타이머가 정상 시작되는가.

## 3. 종합 판정 (이번 실행 기준)

- **에이전트가 확인할 수 있는 범위(유닛 테스트+타입체크)는 전부 통과**했다.
- **제품의 핵심 가치(신뢰할 수 있는 알림)를 포함한 실사용 시나리오는 이번 실행에서 검증하지 못했다** — 이는 실패가 아니라 검증 수단(실기기)이 에이전트에게 없기 때문이다. mission.md §5 성공 기준을 완전히 충족했다고 아직 말할 수 없다.
- 따라서 이번 판정을 "테스트 전부 통과"로 성급하게 확정하지 않는다. 다음 작업(T-015)에서 사람에게 실기기 검증을 요청하고, 그 결과가 나와야 test phase 완료 여부(→ review 전이)를 결정할 수 있다.

## 4. 왜 이 판정이 틀렸을 수 있는가
- 유닛 테스트가 전부 통과해도, 실제 UI 조합(예: 타이머 3개를 빠르게 연속으로 일시정지/재개)에서 `screens/Home.tsx` 의 `notificationIdsRef` 관리 로직에 레이스 컨디션이 있을 수 있다 — 이 부분은 컴포넌트 테스트로 다뤄지지 않았다(설계상 순수 로직만 테스트하기로 함, docs/design/mvp.md §5).
- lint 를 건너뛴 것이 사소한 코드 품질 문제를 놓쳤을 가능성이 있다.
