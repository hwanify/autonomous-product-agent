# 비판적 검토 — Run #20 (review phase, T-016)

> 요리용 멀티 타이머 MVP. 핵심 가설(알림 신뢰성)이 실기기에서 검증된 뒤 첫 review.
> "사용자가 왜 이걸 안 쓸까?"를 먼저 생각하고 코드 전체(`App.tsx`, `screens/Home.tsx`, `components/*.tsx`, `lib/*.ts`)를 다시 읽었다.

## 치명 (Critical)

없음. 핵심 시나리오(타이머 생성 → 동시 실행 → 백그라운드/종료 상태 알림)는 실기기에서 끝까지 동작함이 확인됐다(D-018).

## 높음 (High)

### H1. 앱을 완전히 종료했다가 재실행하면 실행 중이던 타이머 목록이 통째로 사라진다
- **재현**: `screens/Home.tsx` 의 `timers` 상태는 `useState([])` 로 초기화되며 어디에도 영속화되지 않는다. 앱 프로세스가 종료(kill)되면 이 상태는 완전히 사라지고, 재실행 시 항상 빈 리스트로 시작한다.
- **실사용 확인**: 사람이 실기기에서 직접 재현·보고함("앱을 껐다키면 ui는 사라져있어", Run #19).
- **왜 문제인가**: 예약된 로컬 알림 자체는 OS 가 들고 있어 정상적으로 울리지만(핵심 가치는 지켜짐), 사용자 입장에서는 "타이머가 몇 개 돌고 있었는지, 뭐였는지" 화면으로 전혀 확인할 수 없다. 요리 중에 앱이 백그라운드에서 종료되는 일(iOS 메모리 회수, 사용자의 실수로 스와이프 종료 등)은 드물지 않은데, 그때마다 진행 상황을 완전히 잃는다.

### H2. (H1의 직접적 파생) 상태 손실로 인한 잠재적 중복 알림
- **시나리오**: 타이머가 "running" 상태로 앱이 종료되면 알림은 이미 예약돼 있다. 사용자가 재실행 후 빈 화면을 보고 "저장이 안 됐나보다"고 생각해 **같은 타이머를 다시 시작**하면, 원래 예약(오래된 시작 시각 기준)과 새로 예약한 알림이 **둘 다** 남아있게 되어 같은 요리에 대해 시간차를 두고 알림이 두 번 온다.
- **근거**: `screens/Home.tsx` 의 `notificationIdsRef`(예약된 알림 id 추적용)도 컴포넌트 상태와 함께 완전히 초기화되므로, 재실행 후에는 종료 전에 예약해둔 알림을 취소할 방법이 코드상 전혀 없다.
- **왜 높음인가**: H1은 "불편함"이지만 H2 는 실제로 잘못된 정보(중복 알림)를 사용자에게 준다 — 신뢰성이 핵심 가치인 앱에서 이는 가볍지 않다.

### H3. 알림 권한을 나중에 설정에서 켜도 앱을 완전히 재시작하기 전까지는 반영되지 않아 핵심 기능이 무기한 막힌다 (Critic 지적, 코드로 확인)
- **근거**: `screens/Home.tsx` 의 `useEffect(() => { ...; ensureNotificationPermission().then(setPermissionGranted); ... }, [])` 는 **마운트 시 딱 한 번만** 권한을 확인한다. `AppState` 변화(백그라운드→포그라운드 복귀)를 감지하는 리스너가 전혀 없다.
- **재현 시나리오**: 최초 실행 시 iOS 권한 팝업에서 실수로(또는 의도적으로) "허용 안 함"을 누른 사용자가, 나중에 설정 앱에서 알림 권한을 켜고 다시 이 앱으로 돌아와도 `permissionGranted` 상태는 여전히 `false` 로 남는다. 그 결과 "시작" 버튼을 눌러도 `startTimer()` 의 `if (!permissionGranted) { Alert.alert(...); return; }` 에 계속 걸려 **앱을 완전히 종료했다가 재실행하기 전까지 타이머를 단 하나도 만들 수 없다** — 사용자는 이 방법(강제 재시작)을 알 도리가 없다.
- **왜 높음인가**: H1/H2 는 알림이라는 부가 신뢰성 문제인데, H3 는 이 앱의 **가장 기본적인 동작(타이머 시작 자체)을 완전히 막는다.** "처음에 권한 팝업을 무심코 거부했다가 나중에 마음을 바꾸는" 흐름은 실제로 흔하다.

## 중간 (Medium)

### M1. "시작" 버튼을 눌러도 입력이 비어 있으면 아무 피드백이 없다
- `components/NewTimerModal.tsx` `handleStart()`: `if (!label.trim() || totalSeconds <= 0) return;` — 라벨을 안 쓰거나 시간을 0으로 두고 "시작"을 누르면 그냥 아무 일도 일어나지 않는다(모달이 안 닫히고 에러 메시지도 없음). 사용자는 왜 안 되는지 알 방법이 없다.

### M2. 프리셋 삭제(×) 버튼이 칩 경계를 넘어 인접 칩과 터치 영역이 겹칠 수 있다
- `components/PresetList.tsx`: 삭제 버튼이 `position:'absolute', top:-6, right:-6`(지름 20)으로 칩 바깥에 걸쳐 있고, 칩 사이 간격(`gap:10`)이 좁아 오른쪽 칩의 삭제 버튼과 다음 칩의 탭 영역이 실기기 화면 밀도에 따라 겹칠 여지가 있다. 실기기에서 좁은 간격으로 여러 프리셋을 만들었을 때 오터치(원하는 프리셋을 시작하려다 옆 프리셋을 삭제)로 이어질 수 있다.

### M3. 완전히 같은 라벨+시간의 프리셋이 중복 저장될 수 있다
- `screens/Home.tsx` `handleCreate()`: 기존 프리셋과 라벨/시간이 같은지 확인하지 않고 무조건 `addPreset` 한다. 실수로 같은 프리셋을 여러 번 저장하면 프리셋 목록이 지저분해진다.

## 낮음 (Low)

### L1. 1시간이 넘는 타이머는 "125:00"처럼 시:분 구분 없이 표시된다
- `components/TimerCard.tsx` `formatMMSS()` 는 시간 단위를 다루지 않는다. 요리 타이머 특성상 대부분 문제 없지만(장시간 저온조리 등 예외 있음), 가독성이 떨어진다.

### L2. 알림 권한이 거부된 경우 설정 앱으로 안내하는 링크가 없다
- `screens/Home.tsx` `startTimer()`: `Alert.alert('알림 권한이 없습니다', '설정에서 알림 권한을 허용해주세요.')` 만 띄우고, 실제로 설정 앱을 열어주는 딥링크(`Linking.openSettings()`)는 없다. 사용자가 직접 설정 앱을 찾아가야 한다.

## 보안
특별한 문제 없음. 서버 호출·계정·유료 API 없음(mission.md §3 준수). 사용자 입력(라벨)은 `<Text>` 로만 렌더링되어 인젝션 위험 없음. 저장 데이터(프리셋)는 로컬 AsyncStorage 에 평문 저장되지만 개인식별정보가 아님.

## 성능
타이머/프리셋 개수가 개인 요리용으로 현실적인 범위(수 개~십여 개) 내에서는 `FlatList`/`ScrollView` 렌더링, `Array.find`/`map` 등에 성능 문제가 없다. 별도 프로파일링 불필요.

## 미션 적합성 / 경쟁 대비 가치 (재확인)
explore 단계(D-005~D-009)에서 이미 비판적으로 검증됨: 시장은 포화 상태이고 유일한 실질적 차별점은 "확실한 알림"이며, 이번에 실기기로 검증됐다(D-018). 이 review 에서 새로 발견된 것은 없다 — 다만 H1/H2 처럼 "확실한 알림"이라는 차별점 자체를 사용자가 화면에서 체감하지 못하게 만드는 결함이 있다는 점이 아이러니하다: 알림은 오는데 그걸 만든 타이머의 기록이 없어 보인다.

## 종합 판정
- 치명 0건, **높음 3건**(H1·H2 는 같은 근본 원인 한 쌍, H3 는 별개), 중간 3건, 낮음 2건.
- CLAUDE.md §3 전이 규칙에 따라 **높음 문제가 있으므로 improve 단계로 진행**해야 한다.
- **improve 우선순위 1건: H3(알림 권한 재확인, `AppState` 리스너 추가)를 먼저 고친다.** H1/H2(타이머 영속화)보다 H3 를 먼저 선택한 이유:
  1. H3 는 "부가 신뢰성 저하"가 아니라 **핵심 동작(타이머 생성 자체)을 완전히 막는다** — 최초 권한 팝업을 거부했다가 나중에 마음을 바꾸는 사용자에게는 이 앱이 사실상 고장난 것과 같다.
  2. 수정 범위가 작고 명확하다(`AppState` 변화 감지 + 포그라운드 복귀 시 권한 재조회 1곳 추가) — CLAUDE.md §3.1 예산 원칙에 맞는 작은 단위.
  3. H1/H2(타이머 영속화 + 알림 정합성)는 저장 스키마 설계, 복원 로직, 알림 재동기화까지 얽혀 있어 범위가 크다 — 다음 improve 사이클(test→review→improve 루프가 반복됨, CLAUDE.md §3)로 넘긴다.
- M1~M3, L1~L2, 그리고 H1/H2(이번엔 착수하지 않음)는 이번 improve 대상에서 제외하고 다음 리뷰/개선 사이클 후보로 backlog 에 남긴다.

## Critic 게이트 반영 이력
1차 제출본은 H1/H2(치명 0/높음 2건)만 다뤘으나, 독립 Critic 이 코드를 직접 읽고 H3(알림 권한 재확인 누락)를 놓쳤다고 지적(REWORK). 코드로 재확인한 결과 지적이 정확해 H3 를 추가하고 improve 우선순위를 H3 로 변경했다.

## 이 판정이 왜 틀렸을 수 있는가
1. H2(중복 알림)는 사용자가 실제로 "다시 시작"하는 행동을 할 것이라는 가정에 근거한 추론이다 — 실제로 사용자가 그렇게 행동할지, 아니면 그냥 무시하고 넘어갈지는 관찰되지 않았다. 과대평가일 수 있다.
2. M2(터치 영역 겹침)는 코드 상 가능성으로 추론한 것이지 실기기에서 직접 오터치를 재현한 것은 아니다.
3. H1 을 "높음"으로 매긴 것 자체가 관대할 수 있다 — 핵심 기능(알림)은 살아있으므로 "중간"으로 낮춰 볼 여지도 있다. 다만 신뢰성이 이 제품의 유일한 가치 제안이라는 점에서 상태 손실이 그 신뢰를 갉아먹는다고 보아 높음으로 유지했다.
4. H3 를 H1/H2 보다 먼저 고치기로 한 순서 판단도 틀렸을 수 있다 — H1/H2(중복 알림)가 실제로는 더 자주 발생하는 시나리오라면(예: iOS 가 메모리 부족 시 백그라운드 앱을 자주 강제 종료하는 경우) 순서를 바꿔야 할 수 있다. 이는 다음 리뷰에서 재검토한다.
